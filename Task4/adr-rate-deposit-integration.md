### Название задачи:
ADR: Интеграция кол-центра и партнёрского кол-центра с модулем ставок

### Автор:
Архитектор команды цифровой трансформации

### Дата:
2026-06-12

### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
|---|------------------------------|----------|----------|
| 1 | Менеджер кол-центра банка | Просмотр актуальных ставок по депозитам | Менеджер в интерфейсе системы кол-центра видит текущие ставки для консультации клиентов |
| 2 | Система кол-центра банка | Получение ставок из Rate Management Service | Система кол-центра через REST API получает актуальные ставки и кеширует их для быстрого доступа |
| 3 | Сотрудник бэк-офиса | Обновление ставок | Сотрудник меняет ставки через веб-интерфейс Rate Management Service, изменения сразу доступны всем системам |
| 4 | Rate Management Service | Экспорт ставок в файл для партнёрского кол-центра | При изменении ставок сервис формирует файл согласованного формата и отправляет на SFTP-сервер партнёра |
| 5 | Партнёрский кол-центр | Загрузка и применение ставок | Партнёр забирает файл со своего SFTP-сервера. Файл используется менеджерами как справочник ставок |
| 6 | Менеджер партнёрского кол-центра | Консультация клиентов по ставкам | Менеджер открывает полученный файл и использует его как справочник для консультации клиентов банка |

### Нефункциональные требования

| № | Требование |
|---|------------|
| 1 | Данные ставок при передаче в кол-центр банка должны быть защищены (HTTPS) |
| 2 | Файлы для партнёрского кол-центра должны передаваться по защищённому каналу (SFTP) |
| 3 | При изменении ставок сотрудником бэк-офиса обновление в кол-центре банка должно происходить в реальном времени (REST API) |
| 4 | Экспорт файла для партнёрского кол-центра должен выполняться автоматически при изменении ставок |
| 5 | Формат файла должен быть согласован с партнёром (CSV, XML или XLSX) |
| 6 | Отказоустойчивость: при недоступности Rate Management Service кол-центр банка использует закешированные данные |
| 7 | Rate Management Service должен логировать все изменения ставок и факты отправки файлов партнёру для аудита |
| 8 | Использовать существующие технологии: Python Flask (Rate Management Service), Java Spring Boot (кол-центр) |

### Решение

**Логика принятия решений:**

1. **Интеграция кол-центра банка с Rate Management Service через REST API** — система кол-центра уже использует Java Spring Boot и имеет опыт интеграций через REST API. Добавляем новый endpoint в Rate Management Service для получения ставок, в кол-центре добавляем клиент с кешированием.

2. **Партнёрский кол-центр — только файловый обмен через SFTP** — партнёр работает во внешней системе, API-интеграция невозможна. Rate Management Service формирует файл и отправляет его на SFTP-сервер партнёра при каждом изменении ставок. Дополнительно файл отправляется раз в сутки как гарантия доставки.

3. **Rate Management Service остаётся мастер-системой по ставкам** — все изменения идут через него, он же отвечает за распространение данных потребителям.

4. **Формат файла — CSV** — простой, легко парсится любой системой, согласовывается с партнёром. Структура: код депозита, название, ставка, срок, мин. сумма, дата обновления.

### Альтернативы

1. **Хранение ставок только в АБС, без Rate Management Service.**
   - Отвергнуто: АБС перегружена, масштабируется только вертикально, прямой доступ внешних систем нежелателен. Rate Management Service уже спроектирован в задании 3.

2. **Передача ставок в кол-центр банка через Kafka.**
   - Отвергнуто: для MVP избыточно. REST API с кешированием на стороне кол-центра достаточно для удовлетворения требований по скорости и надёжности.

3. **Отправка файлов партнёру по email.**
   - Отвергнуто: небезопасно, нет гарантии доставки, сложнее автоматизировать. SFTP — стандартный и безопасный способ файлового обмена.

**Недостатки, ограничения, риски**

- **Файловый обмен с партнёром неявный** — между изменением ставки и появлением файла у партнёра есть задержка. Клиент может получить устаревшую информацию. Риск смягчается автоматической отправкой при каждом изменении.
- **Формат CSV требует согласования** — при изменении структуры данных нужно синхронизировать изменения с партнёром. Необходим процесс версионирования формата.
- **Отказ SFTP-сервера партнёра** — необходимы ретраи и алертинг при ошибках отправки. Файл также отправляется раз в сутки как страховка.
- **Нет API у партнёра** — невозможность проверить, загрузил ли партнёр файл и применил ли ставки. Нужен организационный процесс подтверждения.

### Список задач по системам

**Rate Management Service (Python Flask):**
1. Добавить REST API endpoint для получения актуальных ставок (GET /api/rates)
2. Реализовать формирование файла со ставками при каждом изменении
3. Реализовать отправку файла на SFTP-сервер партнёра (с ретраями и алертингом)
4. Добавить scheduled job для ежесуточной отправки файла как гарантии доставки
5. Добавить логирование изменений ставок и фактов отправки файлов
6. Веб-интерфейс для управления ставками сотрудниками бэк-офиса

**Система кол-центра банка (Java Spring Boot, React):**
1. Добавить REST-клиент для получения ставок из Rate Management Service
2. Реализовать кеширование ставок в PostgreSQL с TTL
3. Доработать веб-интерфейс менеджера: блок с актуальными ставками для консультации
4. Добавить индикатор актуальности данных и дату последнего обновления

**Партнёрский кол-центр (внешняя система):**
1. Предоставить SFTP-сервер и учётные данные для банка
2. Согласовать формат файла со ставками
3. Разработать регламент для менеджеров: использовать файл с актуальной датой обновления
4. Настроить уведомление менеджеров о поступлении нового файла (организационно)

**Инфраструктура банка:**
1. Настроить SFTP-клиент на стороне Rate Management Service
2. Настроить мониторинг и алертинг для ошибок отправки файлов
